### Q1 — Complete checklist to add one provider, with the smallest real provider (DeepInfra) quoted end-to-end

CodexBar has TWO parallel registries per provider, one in each of its two Swift targets, kept in sync by a generator script — this is the actual mechanical process, not a guess:

1. **Add a case to the closed enum** `public enum UsageProvider: String, CaseIterable, Sendable, Codable` in Sources/CodexBarCore/Providers/Providers.swift:21-91 (68 cases today, alphabetically enforced by a `// swiftformat:disable sortDeclarations` block). This one enum is the provider's canonical identity everywhere (persistence keys, CLI flags, icon lookup, settings dictionary keys).
2. **Create exactly one `*ProviderDescriptor.swift`** file anywhere under Sources/CodexBarCore/Providers/<YourProvider>/ that declares `public enum YourProviderDescriptor { public static let descriptor: ProviderDescriptor = ...; static func makeDescriptor() -> ProviderDescriptor { ProviderDescriptor(id: .yourprovider, ...) } }`. This is CodexBarCore (headless: fetch logic, credentials, parsing — usable outside the app, e.g. from `codexbar` CLI/`codexbar serve`).
3. **Create exactly one `*ProviderImplementation.swift`** file under Sources/CodexBar/Providers/<YourProvider>/ conforming to `protocol ProviderImplementation` (Sources/CodexBar/Providers/Shared/ProviderImplementation.swift) — this is the app-only UI-behavior layer (menu entries, settings panes, login flow). Every member except `id` has a default no-op implementation in a protocol extension, so the minimal legal implementation is ~15 lines (see DeepInfra quote below).
4. **Run `Scripts/regenerate-provider-manifests.sh [write|check]`** (verbatim from the script, lines 1-60+): it parses `case <name>` lines out of the UsageProvider enum, then for each name greps `Sources/CodexBarCore/Providers` for exactly one file matching `id: .<provider>,` inside a `*ProviderDescriptor.swift`, and `Sources/CodexBar/Providers` for exactly one `*ProviderImplementation.swift`, and fails hard (`exit 1`) if the count isn't exactly 1 on either side. On success it REWRITES four generated files — never hand-edit these:
   - Sources/CodexBarCore/Providers/ProviderManifest.swift (`public enum ProviderManifest { public static let allDescriptors: [ProviderDescriptor] = [...] }`, header `// Generated by Scripts/regenerate-provider-manifests.sh. Do not edit by hand.`)
   - Sources/CodexBar/Providers/Shared/ProviderImplementationManifest.swift (mirror array of `{ YourProviderImplementation() }` closures)
   - Sources/CodexBarCore/Providers/ProviderInstanceIDAliases.generated.swift
   - docs/provider-ids.md
   CI runs this in `check` mode (Scripts/ci_macos_test_gate.sh references it) so a manifest that's out of sync fails the build.
5. **A ~4,400-line test file enforces the whole shape at once**: `Tests/CodexBarTests/ProviderArchitectureGatekeeperTests.swift`, e.g. `every provider has descriptor and implementation manifest entries` (line 27) asserts `Set(UsageProvider.allCases) == Set(ProviderDescriptorRegistry.all.map(\.id)) == Set(ProviderImplementationRegistry.all.map(\.id))`, and `every provider descriptor has a loadable SVG resource` (line 95) checks a brand icon exists. See finding 6 for the rest of this file's role.

`DeepInfraUsageFetcher.swift` (network + parsing, ~230 lines): defines `DeepInfraChecklistResponse`/`DeepInfraUsageResponse` Decodable structs, `DeepInfraUsageError: LocalizedError` (missingCredentials/networkError/apiError/parseFailed), a `fetchUsage(apiKey:)` that hits two GET endpoints (`https://api.deepinfra.com/payment/checklist?compute_owed=true`, `https://api.deepinfra.com/payment/usage?from=current`) via a shared `ProviderHTTPClient`, and `toUsageSnapshot()` that maps the parsed response into the canonical `UsageSnapshot` (see finding 4).

App-side implementation (Sources/CodexBar/Providers/DeepInfra/DeepInfraProviderImplementation.swift), quoted in full — this is literally the whole file:
```swift
struct DeepInfraProviderImplementation: ProviderImplementation {
    let id: UsageProvider = .deepinfra
    @MainActor func presentation(context _: ProviderPresentationContext) -> ProviderPresentation { ProviderPresentation { _ in "api" } }
    @MainActor func observeSettings(_: SettingsStore) {}
    @MainActor func isAvailable(context: ProviderAvailabilityContext) -> Bool {
        if DeepInfraSettingsReader.apiKey(environment: context.environment) != nil { return true }
        return !context.settings.tokenAccounts(for: .deepinfra).isEmpty
    }
    @MainActor func settingsFields(context _: ProviderSettingsContext) -> [ProviderSettingsFieldDescriptor] { [] }
}
```

For a real OAuth+web+CLI provider (Claude), the same `resolveStrategies` slot instead returns a dynamically ordered array of up to 4 `ProviderFetchStrategy` values (Admin-API key, OAuth, Web-cookie, CLI-subprocess) computed by a dedicated `ClaudeSourcePlanner` (Sources/CodexBarCore/Providers/Claude/ClaudeProviderDescriptor.swift:229-286), each still wired through the same `fetchPlan: ProviderFetchPlan(sourceModes: [.auto, .api, .web, .cli, .oauth], pipeline: ProviderFetchPipeline(resolveStrategies:))` shape — so the *protocol surface* a new provider must fill in is identical in complexity to DeepInfra; only the strategy count grows.

**Takeaway.** Copy the two-registry / two-file-per-provider split (headless CodexBarCore descriptor + app-only ProviderImplementation) — it's what lets `codexbar` CLI and `codexbar serve` work without AppKit. Copy the generator-script + gatekeeper-test pattern too: it is the single biggest reason 68 providers haven't rotted into inconsistent shapes. Use DeepInfraProviderDescriptor.swift/DeepInfraUsageFetcher.swift/DeepInfraSettingsReader.swift + DeepInfraProviderImplementation.swift as the literal starting template for JR-BAR's simplest new provider; for an OAuth+CLI provider start from ClaudeProviderDescriptor.swift's `resolveStrategies` instead.

### Q2 — The two provider protocols, every member and what it controls

**`ProviderDescriptor`** (struct, not protocol — but functions as one via required init args), Sources/CodexBarCore/Providers/ProviderDescriptor.swift:298-358. Required/optional members:
- `id: UsageProvider` — required.
- `metadata: ProviderMetadata` — required. Itself a large struct (Providers.swift:132-226): displayName/shortDisplayName, sessionLabel/weeklyLabel/opusLabel strings for the menu, supportsOpus/supportsCredits/creditsHint, toggleTitle, cliName, defaultEnabled, widgetSelectable, isPrimaryProvider, usesAccountFallback, sharePlanLabels (per-plan share-card copy), debugLogUnavailableMessage, debugPane (ProviderDebugPaneCapabilities: probeLogOrder/notificationSimulationOrder/errorSimulationOrder — controls Preferences → Debug pane ordering), balanceOnly (usage is a $ balance not a %), usesDetailBackedWindow, browserCookieOrder, dashboardURL/subscriptionDashboardURL/changelogURL, statusPageURL/statusLinkURL/statusWorkspaceProductID/statusComponentAllowlist (statuspage.io polling config, independent of the credential/fetch status described in finding 5).
- `branding: ProviderBranding` — required (icon, brand color, confetti palette).
- `tokenCost: ProviderTokenCostConfig` — required. Controls whether/how the $-cost history UI renders: supportsTokenCost, noDataMessage, menuHintLines, supportsTokenSnapshot, estimateDisclaimer, historyTitleStyle, primaryValue (.session vs .latestDaily), hintPlacement.
- `pace: ProviderPaceCapability = .unsupported` — optional. Governs the 'burn rate' / pace projection UI: `resetWindowPace`/`inferredMonthlyDuration` (ProviderPaceWindowRule/.custom closures) plus up to 3 named lanes (`primary`/`secondary`/`tertiary: ProviderStandardPaceLane`, each a `(kind: .session|.weekly, windowRule)`).
- `history: ProviderHistoryCapability = .optIn` — optional; `.alwaysTracked` vs `.optIn` for plan-utilization history charting.
- `presentation: ProviderUsagePresentation = ProviderUsagePresentation()` — optional; menu-bar window resolver closure + card/menu presentation hints.
- `settingsSection: ProviderSettingsSectionRegistration?` — optional, defaults to empty; type-erased per-provider settings struct registration (e.g. `DevinProviderSettingsKey`).
- `credentials: ProviderCredentialAdapter?` — optional (nil for CLI-probe-only providers with no stored secret); see finding 3 for its full shape.
- `config: ProviderConfigCapabilities = ProviderConfigCapabilities()` — optional; workspaceIDValidationOrder, supportsEnterpriseHost.
- `menuBarMetrics: ProviderMenuBarMetricCapabilities?` — optional, defaults to `.automaticOnly` if `metadata.balanceOnly` else `.standard`; which of {automatic, primary, secondary, primaryAndSecondary, tertiary, extraUsage, average, monthlyPlan} the user can pick for the menu-bar number.
- `fetchPlan: ProviderFetchPlan` — **required**, the actual fetch behavior (`sourceModes: Set<ProviderSourceMode>` ∈ {auto, web, cli, oauth, api} + a `ProviderFetchPipeline` closure returning `[any ProviderFetchStrategy]`).
- `cli: ProviderCLIConfig` — required: `name`, `aliases: [String]`, optional `binaryLocator`/`versionDetector`/`supportsCostCommand`/`ttyStatusCommand`/`ttyLaunch: ProviderTTYLaunchConfig` (executableOverrideEnvironmentKey, bundledWatchdogHelperName, probeWorkingDirectory).
- `configNormalizer: @Sendable (inout ProviderConfig) -> Void = { _ in }` — optional, private-set-only-via-init mutation hook.
Registration is via a process-wide singleton, `ProviderDescriptorRegistry` (same file, lines 360-422): a locked `Store` with `ordered`/`byID`, lazily bootstrapped from `ProviderManifest.allDescriptors` on first access, plus a public `register(_:)` that plugin/runtime providers (see `Sources/CodexBarCore/Plugins/`) can call directly to add themselves without a manifest entry.

**`ProviderFetchStrategy`** protocol (Sources/CodexBarCore/Providers/ProviderFetchPlan.swift:243-268) — what an individual strategy inside `fetchPlan` must implement: `var id: String`, `var kind: ProviderFetchKind` (cli/web/oauth/apiToken/localProbe/webDashboard), `func isAvailable(_ context: ProviderFetchContext) async -> Bool`, `func fetch(_ context: ProviderFetchContext) async throws -> ProviderFetchResult`, `func shouldFallback(on error: Error, context: ProviderFetchContext) -> Bool`.

**`ProviderImplementation`** protocol (app layer), Sources/CodexBar/Providers/Shared/ProviderImplementation.swift:9-84. Only `id: UsageProvider` has no default; everything else has a protocol-extension default (lines 86-onward) so a minimal conformer is ~15 lines (DeepInfra, quoted in finding 1). Members: `supportsLoginFlow: Bool` (default false), `presentation(context:) -> ProviderPresentation`, `observeSettings(_:)`, `isAvailable(context:) -> Bool` (default true), `defaultSourceLabel/decorateSourceLabel(context:)`, `sourceMode(context:) -> ProviderSourceMode` (default .auto), `detectVersion(context:) async -> String?` (default delegates to the descriptor's `cli.versionDetector`), `makeRuntime() -> (any ProviderRuntime)?`, `settingsToggles/settingsFields/settingsActions/settingsPickers(context:)` (default `[]` — the doc comment explicitly forbids returning custom SwiftUI views here, only shared descriptor structs), `settingsOrganizations(context:) -> ProviderSettingsOrganizationsDescriptor?`, `tokenAccountsVisibility(context:support:) -> Bool`, `settingsSnapshot(context:) -> ProviderSettingsSnapshotContribution?`, `runTokenAccountPrimaryAction(context:) async`, `applyTokenAccountCookieSource(settings:)`, `appendUsageMenuEntries`/`appendActionMenuEntries(context:entries: inout [ProviderMenuEntry])`, `loginMenuAction(context:) -> (label:String, action:MenuDescriptor.MenuAction)?`, `runLoginFlow(context:) async -> Bool`. Registered the same way as descriptors via `ProviderImplementationRegistry` (Sources/CodexBar/Providers/Shared/ProviderImplementationRegistry.swift), bootstrapped from the generated `ProviderImplementationManifest.makeImplementations: [@Sendable () -> any ProviderImplementation]`.

**Takeaway.** The split is deliberate and worth copying as-is: `ProviderDescriptor`/`ProviderFetchStrategy` in a headless core module = 'can this run in a CLI/daemon with no UI', `ProviderImplementation` in the app module = 'how does it render/behave in the menu bar'. Almost every ProviderImplementation member is optional via defaults — only conform to what you actually customize.

### Q3 — Credentials in exact detail per target provider (Claude, Codex, Cursor, Gemini, Devin, Grok, OpenCode, Antigravity) — service names, paths, env vars, refresh endpoints, redaction

**Claude** (Sources/CodexBarCore/Providers/Claude/ClaudeOAuth/ClaudeOAuthCredentials.swift, +SecurityCLIReader.swift, ClaudeConfigPaths.swift):
- Reads Claude Code CLI's OWN macOS Keychain item: service `"Claude Code-credentials"` (constant `claudeKeychainService`, ClaudeOAuthCredentials.swift:15). No fixed account name is hardcoded — queries are service-only (`kSecAttrService` only, no `kSecAttrAccount` filter) except when using the `/usr/bin/security` CLI path, which optionally passes `-a <account>` from `preferredClaudeKeychainAccountForSecurityCLIRead`.
- Two read mechanisms, switched by a stored preference (`ClaudeOAuthKeychainReadStrategy`: `.securityFramework` vs `.securityCLIExperimental`): (a) `SecItemCopyMatching` directly via Security.framework with `kSecUseAuthenticationUIFail`/no-UI flags (`KeychainNoUIQuery.apply`), or (b) shelling out to `/usr/bin/security find-generic-password -s "Claude Code-credentials" [-a <account>] -w [<isolated-keychain-path>]` as a `Process()` with a 1.5s timeout (`securityCLIReadTimeout`), its own process group, and SIGTERM→SIGKILL escalation (+SecurityCLIReader.swift:216-274,308-324).
- Elaborate NO-PROMPT-BY-DEFAULT gating: `ClaudeOAuthKeychainPromptMode` (never / onlyOnUserAction / always, user-configurable), a cooldown gate (`ClaudeOAuthKeychainAccessGate`), and a pre-alert dialog (`ClaudeOAuthKeychainPreAlertGate`) before ever risking a native Keychain ACL prompt.
- File fallback (used when Keychain is unavailable/disabled, and to detect ownership changes): `ClaudeConfigPaths.credentialsURL` = `$CLAUDE_SECURESTORAGE_CONFIG_DIR/.credentials.json`, else `$CLAUDE_CONFIG_DIR/.credentials.json`, else `~/.claude/.credentials.json` (ClaudeConfigPaths.swift:36-49). `CLAUDE_CONFIG_DIR` env var fully overrides the config root; empty means default `~/.claude`.
- CodexBar's own re-cache: writes the decrypted JSON into ITS OWN Keychain, service `"com.steipete.codexbar.cache"` (KeychainCacheStore.swift:42, constant `cacheService`), account = `"oauth." + provider.rawValue` = `"oauth.claude"` (via `KeychainCacheStore.Key.oauth(provider:)`, KeychainCacheStore.swift:890-892: `Self(category: "oauth", identifier: instanceID.rawValue)`, and `Key.account` = `"\(category).\(identifier)"`). Plus a 30-minute (`memoryCacheValidityDuration = 1800`) in-process memory cache.
- OAuth client id (public, PKCE, not secret): `"9d1c250a-e61b-44d9-88ed-5944d1962f5e"` (`defaultOAuthClientID`), overridable via env `CODEXBAR_CLAUDE_OAUTH_CLIENT_ID`.
- Refresh endpoint: `POST https://platform.claude.com/v1/oauth/token`, `application/x-www-form-urlencoded` body `grant_type=refresh_token&refresh_token=<token>&client_id=9d1c250a-...` (ClaudeOAuthCredentials.swift:1439-1494). Response JSON keys: `access_token`, `refresh_token`, `expires_in`, `token_type`.
- **CRITICAL nuance**: CodexBar only calls this refresh endpoint itself when the credential's `owner == .codexbar` (i.e. CodexBar did its own login flow, not the common case). When `owner == .claudeCLI` (the normal case — Claude Code CLI owns the credential), CodexBar explicitly REFUSES to refresh and throws `ClaudeOAuthCredentialsError.refreshDelegatedToClaudeCLI` (ClaudeOAuthCredentials.swift:1611-1626), then (`ClaudeOAuthDelegatedRefreshCoordinator.swift`) invokes an opaque `claude` CLI status/auth-path 'touch' subprocess and polls the Keychain fingerprint (`waitForClaudeKeychainChange`, hash of modifiedAt/createdAt/persistentRef) until it changes, rather than ever consuming Claude Code's refresh token itself. This exists because Anthropic's refresh tokens are single-use/rotating and CodexBar refreshing them out from under Claude Code used to force users to re-`claude login` (see finding 7, CHANGELOG #1161/#1239/#2745).
- Env var overrides for tests/CI: `CODEXBAR_CLAUDE_OAUTH_TOKEN`, `CODEXBAR_CLAUDE_OAUTH_SCOPES`.
- Model-tier data: `ClaudeScopedWeeklyLimitMapper.swift` (see finding 4) surfaces Anthropic's per-model weekly sub-caps (e.g. an Opus-only weekly lane) from the same usage payload.
- Failure representation: `ClaudeOAuthCredentialsError` enum includes `.notFound`, `.decodeFailed`, `.refreshFailed(String)`, `.noRefreshToken`, `.refreshDelegatedToClaudeCLI`, `.mcpOAuthOnlyKeychain` (detects a Keychain entry that only has MCP OAuth state, not the CLI usage credential), `.keychainError(status: Int)` (raw OSStatus).

**Codex/OpenAI (`codex` provider)** (Sources/CodexBarCore/Providers/Codex/CodexOAuth/CodexOAuthCredentials.swift, CodexTokenRefresher.swift, CodexHomeScope.swift):
- NO Keychain at all. Plaintext file: `$CODEX_HOME/auth.json`, default `~/.codex/auth.json` (CodexHomeScope.ambientHomeURL, respects `CODEX_HOME` env var literally).
- File shape: top-level `tokens: {access_token, refresh_token, id_token?, account_id?}` (accepts both snake_case and camelCase keys) plus `last_refresh` (ISO-8601). Also accepts a flat `{"OPENAI_API_KEY": "..."}` shape for raw API-key auth (`apiKeyCredentials(in:)`).
- `needsRefresh: Bool` = `lastRefresh` older than 8 days (`eightDays = 8*24*60*60`).
- Refresh endpoint: `POST https://auth.openai.com/oauth/token`, JSON body `{client_id: "app_EMoamEEZ73f0CkXaXp7hrann", grant_type: "refresh_token", refresh_token: <token>, scope: "openid profile email"}` (CodexTokenRefresher.swift:6-58). Unlike Claude, CodexBar refreshes this itself directly and writes the new tokens back to auth.json via `CredentialFileWriter.writePrivate` (mode-restricted atomic write).
- Failure kinds: `RefreshError.expired/.revoked/.reused/.networkError/.invalidResponse`, discriminated from the token endpoint's JSON `error`/`error.code` field (`refresh_token_expired`→expired, `refresh_token_reused`→reused, `invalid_grant`/`refresh_token_invalidated`→revoked) or HTTP 401→expired.
- Also has a whole separate `openai` provider (OpenAIAPIProviderDescriptor) for raw platform API keys via `OPENAI_API_KEY`/config — Codex-the-subscription and OpenAI-the-API-key are two DIFFERENT `UsageProvider` cases in CodexBar, worth mirroring in JR-BAR's 'Codex/OpenAI' bucket.
- ChatGPT-web dashboard fallback: `dashboardURL: "https://chatgpt.com/codex/settings/usage"`, scraped via a hidden WebKit view (`OpenAIDashboardFetcher`/`OpenAIDashboardWebViewCache`) when OAuth alone doesn't expose weekly-limit UI data — fetch order `sourceModes: [.auto, .web, .cli, .oauth]` (CodexProviderDescriptor.swift:108-121).

**Cursor** (Sources/CodexBarCore/Providers/Cursor/CursorStatusProbe.swift): two independent sources, no Keychain, no auth.json:
1. Cursor.app's own local state: SQLite file `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` (Linux: `$XDG_CONFIG_HOME/Cursor/User/globalStorage/state.vscdb`), read read-only via a vendored SQLite3 C shim, `SELECT value FROM ItemTable WHERE key = ?` with key `"cursorAuth/accessToken"` (CursorStatusProbe.swift:454-520). The value is a JWT; `sub` claim (after the last `|`) is the user id, `exp` claim is expiry (must be >60s out to count as usable).
2. Browser session cookies for domains `cursor.com`/`cursor.sh`/`authenticator.cursor.sh`, cookie names `WorkosCursorSessionToken`, `__Secure-next-auth.session-token`, `next-auth.session-token`, `authjs.session-token`, `__Secure-authjs.session-token` (CursorStatusProbe.swift:26-43), imported via the vendored `SweetCookieKit`/`BrowserCookieClient` per-browser cookie-jar reader.
- Either source is converted to the same API auth header: `WorkosCursorSessionToken=<userID>%3A%3A<accessToken>` (CursorStatusProbe.swift:399-401).

**Gemini** (Sources/CodexBarCore/Providers/Gemini/GeminiOAuthConfig.swift, GeminiConsumerTierMigration.swift): OAuth client id/secret resolved from env vars `GEMINI_OAUTH_CLIENT_ID`/`GEMINI_OAUTH_CLIENT_SECRET` (mirrors the Gemini CLI's own installed client, per the doc comment 'Mirrors Antigravity's env override pattern'), plus `GEMINI_OAUTH2_JS_PATH`. **Important policy note** (see finding 7): as of the file's own comment, 'Google no longer supports Gemini CLI OAuth for individual, AI Pro, or Ultra accounts' (June 2026 shutdown) — CodexBar's Gemini provider now effectively only serves Workspace/education accounts; consumer accounts are redirected to the Antigravity provider.

**Devin** (Sources/CodexBarCore/Providers/Devin/DevinUsageFetcher.swift/DevinProviderSettings.swift): `baseURL = https://app.devin.ai`. Two credential sources, both surfacing as a bearer token: browser session cookies for `devin.ai`/`*.devin.ai` (via `settings.cookieSource`), or a user-pasted manual bearer token (`settings.devin.manualBearerToken`, `Authorization: Bearer <token>` header, DevinUsageFetcher.swift:184). No OAuth, no Keychain, no local auth file.

**Grok** (Sources/CodexBarCore/Providers/Grok/GrokAuth.swift): plaintext file, no Keychain: `$GROK_HOME/auth.json`, default `~/.grok/auth.json`. Shape: a JSON object keyed by OAuth **scope URL**, not a flat token — each entry has `key` (the bearer token, field literally named `key`), `refresh_token`, `auth_mode`, `user_id`, `email`, `first_name`/`last_name`, `team_id`, `principal_type`, `oidc_issuer`, `oidc_client_id`, `expires_at`, `create_time`. Two known scopes: `oidcScopePrefix = "https://auth.x.ai::"` (OIDC, SuperGrok subscribers — preferred) and `legacySessionScope = "https://accounts.x.ai/sign-in"` (older `grok login` sessions) — `selectPreferredEntry` prefers OIDC and only falls back to legacy if OIDC's `key` is missing/empty.

**OpenCode** (Sources/CodexBarCore/Providers/OpenCode/OpenCodeCookieImporter.swift, OpenCodeUsageFetcher.swift): browser-cookie-only, no local auth file. Cookie domains `opencode.ai`/`app.opencode.ai`; requires an `auth` or `__Host-auth` cookie to be present (silently skips cookie jars that have other cookies but not that one). Fetches hit `https://opencode.ai/_server` — an internal RPC endpoint addressed by opaque hex 'server function IDs' reverse-engineered from the web app, e.g. `workspacesServerID = "def39973..."`, `subscriptionServerID = "7abeebee..."`, `billingServerID = "c83b78a6..."` (OpenCodeUsageFetcher.swift:26-37) — this is scraping an undocumented internal API, not a published one, with a spoofed desktop-Chrome `User-Agent`. Field-name parsing is deliberately defensive against upstream renames: `percentKeys`/`resetInKeys`/`resetAtKeys`/`renewAtKeys` are each arrays of 6-10 candidate JSON key names tried in order (lines 39-63) — direct evidence of Q7-style schema-drift absorption baked into the parser itself.

**Antigravity** (Sources/CodexBarCore/Providers/Antigravity/AntigravityOAuthCredentialsStore.swift): full Google OAuth2 flow CodexBar owns end-to-end. `authURL = https://accounts.google.com/o/oauth2/v2/auth`, `tokenURL = https://oauth2.googleapis.com/token`, `userInfoURL = https://www.googleapis.com/oauth2/v2/userinfo`, scopes `["https://www.googleapis.com/auth/cloud-platform", "https://www.googleapis.com/auth/userinfo.email"]`. Client id/secret resolution, in order: (1) env vars `ANTIGRAVITY_OAUTH_CLIENT_ID`/`ANTIGRAVITY_OAUTH_CLIENT_SECRET`; (2) **auto-discovery by scanning the installed Antigravity.app/Gemini.app bundle's Electron/language-server binaries** for a Google client-id pattern `\d+-[A-Za-z0-9_-]+\.apps\.googleusercontent\.com` and a client-secret pattern `GOCSPX-[A-Za-z0-9_-]{28}` (regex + raw-byte scanning fallback, `discoverClientFromInstalledApp`/`parseClient(fromInstalledArtifactData:)`, lines 182-383) — because Google doesn't publish these, CodexBar extracts them from the app it's impersonating, since Antigravity itself is effectively a Gemini-CLI-alike client using its own registered OAuth client. Credentials are cached at `~/.codexbar/antigravity/oauth_creds.json` (NOT Keychain), file mode `0600` (`applySecurePermissionsIfNeeded`), JSON accepts both snake_case and camelCase key variants for robustness against version drift. Env var `ANTIGRAVITY_OAUTH_CREDENTIALS_JSON` can inject credentials directly for tests/headless. There's also a separate local/ambient path (`AntigravityCLISession.swift`, `AntigravityLocalhostSession.swift`) that talks to a locally running `agy` (Antigravity CLI) process instead of doing OAuth itself.

**Universal logging redaction** (Sources/CodexBarCore/Logging/LogRedactor.swift, 62 lines, applies to ALL providers before any log line is written): regexes strip/replace email addresses (`<redacted-email>`), `Bearer <token>` (`Bearer <redacted>`), `Cookie: ...` and `Authorization: ...` header values (`$1<redacted>`), and provider-specific secret shapes `sk-cp-...`/`sk-api-...` (MiniMax) — gated by a cheap `mayContainSensitiveValue` prefilter so most log lines skip regex work entirely. Raw access/refresh tokens are additionally kept OUT of `ProviderFetchResult` by design — the Claude fetch result carries only a `claudeOAuthHistoryOwnerIdentifier: String?` described in-code as 'A one-way discriminator derived from the winning Claude OAuth credential. Raw access and refresh tokens never enter the fetch result or persisted history' (ProviderFetchPlan.swift:121-123) and a `claudeOAuthKeychainPersistentRefHash: String?` ('the raw Keychain reference never enters the persisted usage snapshot', line 119-120).

**Takeaway.** Three fundamentally different credential shapes to replicate in JR-BAR, per provider: (1) read-another-app's-Keychain-item read-only + never-refresh-it-yourself pattern (Claude) — copy this exactly for anything with a CLI that owns rotating refresh tokens; (2) plain JSON auth files with your own direct-refresh (Codex, Grok) — simplest, safest to copy first; (3) full self-owned OAuth with client secrets extracted from an installed app binary (Antigravity) — only copy if there's truly no published client id. Always add: your own re-cache under your own app's Keychain service/account namespace, a redaction layer before any log write, and 0600 permissions plus atomic+fsync writes on any plaintext credential file.

### Q4 — Canonical usage snapshot: parsing → RateWindow/NamedRateWindow/UsageSnapshot, and Claude's model-tier sub-cap mapping

Defined in Sources/CodexBarCore/UsageFetcher.swift:3-296 (all three types quoted near-verbatim below; field lists exact).

`RateWindow` (Codable/Equatable/Sendable, lines 3-96) — the atomic 'one quota bar' unit: `usedPercent: Double` (intentionally NOT globally clamped — display code clamps separately via `UsagePercent.displayClamped` so raw over-100% values survive for diagnostics), `windowMinutes: Int?`, `resetsAt: Date?`, `resetDescription: String?` (free text, used for e.g. Claude CLI's scraped human string), `nextRegenPercent: Double?` (rolling-recovery providers), `isSyntheticPlaceholder: Bool` (defaults false on decode for backward compat) — explicitly documents a real bug-shaped edge case: 'Claude web returns a 0% five-hour window when five_hour is null (an account with no live session but a real weekly lane)'; lane classifiers must treat that as 'no session lane present', not a genuine empty session. Has a `backfillingResetTime(from cached:)` helper that carries a previous cycle's `resetsAt`/`windowMinutes` forward when the fresh payload omits them, while explicitly preserving `isSyntheticPlaceholder` so a backfilled placeholder can't masquerade as real.

`NamedRateWindow` (lines 98-141) — how EXTRA/named rate windows are represented: `id: String`, `title: String` (user-facing, e.g. 'Opus only'), `window: RateWindow`, `usageKnown: Bool` (defaults true on decode; false means 'we know the reset metadata but not real usage yet — render the reset info, but don't paint this as an exhausted quota').

`UsageSnapshot` (Codable/Sendable, lines 143-296) — the canonical top-level model returned by EVERY provider's fetch, regardless of shape: `primary`/`secondary`/`tertiary: RateWindow?` (the up-to-3 headline lanes), `extraRateWindows: [NamedRateWindow]?` (arbitrary additional named lanes — this is the general mechanism, e.g. per-model weekly sub-caps), `providerCost: ProviderCostSnapshot?` (used/limit/currencyCode/period/updatedAt — $ spend vs budget), `details: [ProviderDetailSection]` (capped at `ProviderDetailSection.maximumSectionsPerSnapshot`, enforced by a `precondition` in `init`), plus a long tail of PROVIDER-SPECIFIC OPTIONAL FIELDS bolted directly onto the shared struct rather than modeled as an enum/associated-value payload: `deepseekDetailedUsageState`, `deepseekPlatformProfiles`, `opencodegoUsage: OpenCodeGoUsageSnapshot?`, `openAIAPIUsage: OpenAIAPIUsageSnapshot?`, `codexResetCredits: CodexRateLimitResetCreditsSnapshot?`, `mistralUsage: MistralUsageSnapshot?`, plus three Command-Code-specific live-only Bool markers, `subscriptionExpiresAt`/`subscriptionRenewsAt: Date?`, `updatedAt: Date`, `identity: ProviderIdentitySnapshot?` (accountEmail/accountOrganization/loginMethod — kept siloed per-provider, per the ProviderImplementation doc comment 'Do not mix identity fields across providers'), `dataConfidence: UsageDataConfidence` (.exact/.unknown/etc — feeds the Q5 UI distinction). Several `.with(...)` copy-mutator methods exist for post-fetch enrichment passes (e.g. `.withCodexResetCredits`, `.with(extraRateWindows:)`) rather than re-fetching.

**Model-tier lane mapping, Claude specifically** — `ClaudeScopedWeeklyLimitMapper.swift` (39 lines), shared by both Claude usage-API code paths: takes Anthropic's raw `limits` array (each entry: `kind: String?`, `group: String?`, `percent: Double?`, `resetsAt: Date?`, `modelID: String?`, `modelName: String?`) and maps ONLY entries where `group == "weekly" && kind == "weekly_scoped"` and the model isn't the synthetic 'all models' aggregate (`isAllModelsScope`) into `NamedRateWindow(id: "claude-weekly-scoped-<slugified-model>", title: "<modelName> only", window: RateWindow(usedPercent: percent, windowMinutes: 7*24*60, resetsAt: limit.resetsAt))`. ### Q5 — Error / unavailable / unsupported representation, and how the UI tells them apart

Three-layer error model, all in Sources/CodexBarCore/Providers/ProviderFetchPlan.swift:
1. **Not configured / not attempted**: `ProviderFetchStrategy.isAvailable(_:) async -> Bool` (line 246) is checked BEFORE `fetch()` is ever called. If false, the pipeline (`ProviderFetchPipeline.fetch`, lines 287-345) records `ProviderFetchAttempt(strategyID:, kind:, wasAvailable: false, errorDescription: nil)` and moves to the next strategy WITHOUT ever calling `fetch()` or surfacing an error string — this is the 'not configured' state (e.g. no API key set, no cookie present). If every strategy in the plan is unavailable, the terminal error is `ProviderFetchError.noAvailableStrategy(UsageProvider)` → `"No available fetch strategy for \(provider.rawValue)."` (with a provider-specific override for Kiro pointing at install docs, lines 188-199) — this is the top-level 'provider not configured at all' error shown to the user.
2. **Failed (attempted but errored)**: if `isAvailable` is true but `fetch()` throws, the attempt is recorded `wasAvailable: true, errorDescription: error.localizedDescription`, and the strategy's own `shouldFallback(on:context:)` decides whether the pipeline tries the next strategy or stops and surfaces the error immediately. Errors are optionally classified via `ProviderFetchClassifiedError` (Equatable, LocalizedError, lines 202-232) with an explicit `Kind` enum — 8 buckets: `authenticationExpired`, `missingCredential`, `permissionDenied`, `rateLimited`, `providerUnavailable`, `parseFailure`, `networkFailure`, `apiFailure` — plus an optional `retryAfterSeconds` (clamped to `maximumRetryAfterSeconds = 10`) that `ProviderFetchDelayedRetry.run` (lines 348-368) uses to transparently sleep-and-retry once before giving up. `ProviderFetchOutcome` (lines 178-186) bundles the final `Result<ProviderFetchResult, Error>` with the FULL ordered list of `attempts: [ProviderFetchAttempt]` — so the UI/diagnostics layer can show exactly which strategies were tried, in what order, and why each failed, not just the last error.
3. **Unsupported (platform/build-time)**: providers or code paths that don't exist on a platform are compiled out via `#if os(macOS)` guards (e.g. Cursor's SQLite reader, OpenCode's cookie importer both wrap their entire implementation in `#if os(macOS) ... #else` with a stub that always fails) rather than represented as a runtime error kind — 'unsupported' is a compile-time/build-target distinction, not a `ProviderFetchClassifiedError.Kind` case. There's also `ProviderConfigCapabilities.supportsEnterpriseHost`/etc. as a static per-provider capability flag the UI reads to hide inapplicable settings entirely rather than showing a disabled control.
UI surface: the menu-row-level type is `MenuDescriptor.Entry.unavailable(String, String?)` (Sources/CodexBar/MenuDescriptor.swift:27) — title + optional detail, rendered as a non-actionable(ish) row. Preferences pane surfaces the SAME underlying error text via `ProviderErrorView` (Sources/CodexBar/PreferencesProviderErrorView.swift) — a truncated 3-line preview + 'Show details' disclosure + a copy-to-clipboard button, driven by a `ProviderErrorDisplay(preview:, full:)`. (Note: there's a separate, unrelated `ProviderStatusIndicator` enum in Sources/CodexBar/UsageStoreSupport.swift that maps statuspage.io component states — operational/degraded/partial_outage/major_outage/under_maintenance — to a traffic-light icon; that's upstream-service-health, orthogonal to the credential/fetch-outcome error model above. Don't conflate the two when copying.)

**Takeaway.** Copy the isAvailable()-before-fetch() split as the not-configured/failed boundary — it's the cleanest part of this design and directly gives you three UI states for free: gray/dim (not configured, no error text), red with error detail (failed, classified Kind + optional retry), and hidden entirely (compile-time unsupported). Keep the full attempts[] trail on every outcome, not just the last error — it's what makes their diagnostics/debug pane useful and is cheap to carry.

### 2. The driver interface — every method, guarantees, lifecycle/state reporting

Two distinct interfaces, both in apps/server/src/provider/, both verified live-identical:

A) `ProviderDriver<Config, R>` (ProviderDriver.ts:119-157) — the SPI a Drivers/*.ts file implements. Fields: `driverKind: ProviderDriverKind`; `metadata: { displayName; supportsMultipleInstances? }` (ProviderDriver.ts:43-53, default true, set false for drivers wrapping a global resource e.g. a single desktop-app socket); `configSchema: Schema.Codec<Config, unknown>` — decoded exactly once per (re)load by the registry, a decode failure becomes `ProviderDriverError` downgraded to an unavailable shadow, never a crash (comment at ProviderDriver.ts:122-137); `defaultConfig(): Config`; `create(input: ProviderDriverCreateInput<Config>) => Effect<ProviderInstance, ProviderDriverError, R | Scope.Scope>`. Guarantee documented at ProviderDriver.ts:114-117: 'create is responsible for *all* per-instance state ... and must release them when its scope closes. Two calls to create with different instanceId/config MUST yield instances with no shared mutable state.' `create` must not throw defects — failures become unavailable shadow snapshots (ProviderDriver.ts:150-152).

B) `ProviderAdapterShape<TError>` (Services/ProviderAdapter.ts:45-126) — the actual runtime operations `ProviderService` routes to. Full method list: `provider: ProviderDriverKind`; `capabilities: { sessionModelSwitch: 'in-session'|'unsupported' }`; `startSession(input: ProviderSessionStartInput) => Effect<ProviderSession, TError>`; `sendTurn(input: ProviderSendTurnInput) => Effect<ProviderTurnStartResult, TError>`; `interruptTurn(threadId, turnId?) => Effect<void, TError>`; `respondToRequest(threadId, requestId, decision) => Effect<void, TError>`; `respondToUserInput(threadId, requestId, answers) => Effect<void, TError>`; `stopSession(threadId) => Effect<void, TError>`; `listSessions() => Effect<ReadonlyArray<ProviderSession>>`; `hasSession(threadId) => Effect<boolean>`; `readThread(threadId) => Effect<ProviderThreadSnapshot, TError>`; `rollbackThread(threadId, numTurns) => Effect<ProviderThreadSnapshot, TError>`; `stopAll() => Effect<void, TError>`; `streamEvents: Stream.Stream<ProviderRuntimeEvent>` — the canonical outbound event feed.

Lifecycle/state reporting: `ProviderSession.status` (contracts/provider.ts:26-32) is one of `connecting|ready|running|error|closed`; every runtime state change must surface as a `ProviderRuntimeEvent` (contracts/providerRuntime.ts, 1214 lines) on `streamEvents`, whose canonical session states are `starting|running|waiting|ready|interrupted|stopped|error` (orchestrationSessionStatusFromRuntimeState, apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts:271-289) — this is the shape every driver, native or ACP, must translate into.

Error taxonomy (Errors.ts, live-identical): `ProviderAdapterError = ProviderAdapterValidationError | ProviderAdapterSessionNotFoundError | ProviderAdapterSessionClosedError | ProviderAdapterRequestError | ProviderAdapterProcessError` (Errors.ts:190-195); `ProviderDriverError` (Errors.ts:145-157) is specifically 'a driver create call failed before producing an instance ... surfaced to the registry, which marks the offending entry as an unavailable shadow snapshot rather than crashing the server.'

**Takeaway.** Two-layer contract: `ProviderDriver` (construction/config SPI, must never throw, must isolate per-instance state) wraps a `ProviderAdapterShape` (12 runtime methods + one event stream) that every harness — native or ACP — must implement identically, converging on one canonical 7-state session status enum.

### 3. Deep native driver vs generic ACP adapter — when, and the fidelity cost

Split confirmed by dependency grep and file sizes (apps/server/src/provider/Layers/*.ts line counts, verified): Claude=4591 lines (deep, uses `@anthropic-ai/claude-agent-sdk` in-process — no subprocess spawn of the `claude` CLI at all, per ClaudeAdapter.test.ts's `FakeClaudeQuery implements AsyncIterable<SDKMessage>`), Codex=1997 lines (deep, uses `effect-codex-app-server` package, its own JSONL rollout protocol wrapper), OpenCode=1721 lines (deep-ish, uses `@opencode-ai/sdk/v2`'s `createOpencodeClient` against a spawned `opencode serve` process — detects readiness via `OPENCODE_SERVER_READY_PREFIX = "opencode server listening"`, opencodeRuntime.ts:1-40). Cursor=1182 lines and Grok=1464 lines both go through the generic path: **ACP = Agent Client Protocol**, per the real spec at agentclientprotocol.com (cited directly in doc comments in packages/effect-acp/src/client.ts:44-70, e.g. `@see https://agentclientprotocol.com/protocol/schema#initialize`).

The generic-path stack, bottom to top: `packages/effect-acp` (a full from-scratch Effect implementation of ACP — JSON-RPC-over-stdio client (client.ts, 585 lines) + server-side `AcpAgent` (agent.ts, 537 lines, used by both the real Grok/Cursor CLIs *and* T3 Code's own test mock peers) + wire schema generated into `_generated/schema.gen.ts`/`meta.gen.ts` from scripts/generate.ts + errors.ts (378 lines, typed `AcpProcessExitedError`/`AcpRequestError`/etc.) + protocol.ts (574 lines, JSON-RPC framing/logging)) → `apps/server/src/provider/acp/AcpSessionRuntime.ts` (1005 lines, shared session state machine: spawns the subprocess, does ACP `initialize`→`authenticate`→`session/new or load`, exposes `setSessionModel`, `getConfigOptions`, session-load-replay-idle-gap timeout of 2s / session-load-timeout of 90s) + `AcpRuntimeModel.ts` (582 lines, parses ACP session/update notifications into `AcpParsedSessionEvent`) + `AcpAdapterSupport.ts` (56 lines, tiny — maps `AcpProcessExitedError`→`ProviderAdapterSessionClosedError`, `AcpRequestError`→`ProviderAdapterRequestError`, and maps T3's `ProviderApprovalDecision` to ACP's `allow-always|allow-once|reject-once` permission outcomes) → per-vendor 'Support' files that are genuinely tiny (`CursorAcpSupport.ts` 115 lines: spawns `cursor-agent [-e <endpoint>] acp`, `authMethodId: "cursor_login"`; `GrokAcpSupport.ts` 108 lines: spawns `grok agent stdio` with `GROK_OAUTH2_REFERRER=t3code` env var, `authMethodId` picked between `xai.api_key` (if `XAI_API_KEY` env set) or `cached_token`) → per-vendor 'Extension' files for behavior ACP-proper doesn't cover (`XAiAcpExtension.ts` 432 lines, `CursorAcpExtension.ts` 113 lines — custom prompt-completion / model-picker extensions layered on top of stock ACP methods).

Fidelity cost of the generic path, inferred from the code itself: (a) usage/cost is NOT tracked for ACP drivers at all — `UsageProviderKind = Schema.Literals(["claude","codex"])` (contracts/usage.ts:26) excludes cursor/grok/opencode entirely, i.e. ACP (and OpenCode) drivers get zero on-disk-transcript cost accounting; (b) `sessionModelSwitch` capability differs — the generic ACP model-switch path (`applyGrokAcpModelSelection`, `applyCursorAcpModelSelection`) round-trips through ACP's `session/set_config`/model APIs rather than a native in-band mechanism; (c) each ACP vendor still needed a bespoke ~100-450 line Extension file, i.e. stock ACP alone was insufficient and vendors needed non-standard extensions, meaning the 'generic' protocol is not fully sufficient by itself for full fidelity.

**Takeaway.** Deep native (Claude SDK-in-process, Codex app-server, OpenCode HTTP SDK) is chosen when a vendor exposes a rich native protocol/SDK; ACP (agentclientprotocol.com) is chosen for the long tail (Cursor, Grok) via a shared `effect-acp` + `AcpSessionRuntime` stack, but the generic path still costs real per-vendor Extension code and drops out of usage/cost tracking entirely.

### 4. Provider ACCOUNT/instance model, separate from driver kind

packages/contracts/src/providerInstance.ts (live-identical, header comment lines 1-35 is the design rationale verbatim): 'ProviderDriverKind is the implementation kind selector ... picks which driver package handles the protocol' vs 'ProviderInstanceId is the routing key (a user-defined slug). Threads, sessions, runtime events, and persisted bindings reference instance ids — never driver kinds — so a user can configure multiple instances of the same driver (e.g. codex_personal + codex_work), each with independent driver-specific configuration.' Both are open branded slugs (letters/digits/-/_, 1-64 chars, first char a letter) validated only by pattern, not by a closed enum (providerInstance.ts:58-83) — explicitly for fork/rollback tolerance (unknown driver kinds must decode successfully and degrade to 'unavailable', never fail to parse). `ProviderInstanceConfig` (providerInstance.ts:124-132) is the settings envelope: `{ driver: ProviderDriverKind; displayName?; accentColor?; environment?: ProviderInstanceEnvironment; enabled?; config?: unknown }` — the `config` payload is left `Schema.Unknown` at the contracts layer so each driver owns/decodes its own shape and unknown-driver envelopes round-trip losslessly. `ProviderInstanceConfigMap = Schema.Record(ProviderInstanceId, ProviderInstanceConfig)` is the map stored under `ServerSettings.providerInstances`.

Runtime side: `ProviderInstanceRegistry` (Services/ProviderInstanceRegistry.ts) owns `Map<ProviderInstanceId, ProviderInstance>`, watches settings, and hot-rebuilds an instance's scope when its config entry changes or disappears — 'that's the entire hot-reload story' (file header). `getInstance(id)` returns `ProviderInstance | undefined` (not Option — callers branch on falsy → `ProviderInstanceNotFoundError`). `listUnavailable` surfaces shadow `ServerProvider` snapshots for instances whose driver isn't registered in this build. `ProviderRegistry` (Services/ProviderRegistry.ts) sits above it for snapshot/maintenance routing and documents explicitly (line 25-26): 'Multiple snapshots may share the same provider kind (multiple instances of the same driver) and disambiguate via instanceId.' Migration note baked into the schema comments (providerInstance.ts:141-149, provider.ts:36-39): the legacy single-instance-per-driver world used the driver kind itself as the instance id (`defaultInstanceIdForDriver`), preserved for back-compat routing of pre-migration threads/bindings.

**Takeaway.** Account/instance is a first-class separate entity: `ProviderDriverKind` (open slug, picks the code) is decoupled from `ProviderInstanceId` (user-chosen slug, the actual routing key everywhere in the system), letting one user run e.g. `codex_personal` and `codex_work` as two independently-configured, independently-authed instances of the same driver.

### 5. Usage/cost — on-disk transcript scanning, exact paths, parsing, cost provenance

apps/server/src/usage/UsageService.ts (verified live-identical via `usageTranscripts.ts` blob sha match; UsageService.ts itself only 37-commit-old, same directory untouched by drift). Explicit design statement (UsageService.ts:4-6): 'The scan reads the provider CLIs' own session files rather than T3 Code's orchestration projections, so usage covers turns driven outside T3 Code too. This is the approach ccusage takes.'

SCOPE: only two providers are scanned — `UsageProviderKind = Schema.Literals(["claude","codex"])` (contracts/usage.ts:26). Cursor, Grok, and OpenCode contribute NO usage/cost data in this build.

EXACT PATHS (resolveTranscriptDirs, UsageService.ts:201-226, plus resolveClaudeTranscriptDir:191-198):
- Claude: `resolveClaudeHomePath(settings.providers.claudeAgent)` (Drivers/ClaudeHome.ts:9-15, resolves `homePath` trimmed+expanded via `expandHomePath`, else `os.homedir()`) → probes `<home>/.claude/projects` first, falls back to `<home>/projects` if that nested dir doesn't exist (ClaudeHome override uses `CLAUDE_CONFIG_DIR` env var when set — deliberately NOT `HOME`, because overriding HOME also relocates the macOS keychain lookup and breaks OAuth credential discovery, per comment at ClaudeHome.ts:27-32). Contract doc literally states `~/.claude/projects/**/*.jsonl` (contracts/usage.ts:5).
- Codex: `resolveCodexHomeLayout(settings.providers.codex)` (Drivers/CodexHomeLayout.ts:44-66; default `~/.codex`, or `authOverlay` mode with a separate `shadowHomePath`) → `<sharedHomePath>/sessions`. Contract doc: `~/.codex/sessions/**/*.jsonl` (contracts/usage.ts:5).
Files are walked recursively for `.jsonl` with mtime >= window start minus a `MTIME_SLACK_MS = 36h` (UsageService.ts:66, listTranscriptFiles in usageTranscriptReader.ts:41-74).

PARSING (apps/server/src/usage/usageTranscripts.ts, pure line-reducers, no filesystem access):
- `mightCarryUsage(line, provider)` cheap gate before JSON.parse: Claude lines must contain `"usage"`, Codex lines must contain `"token_count"` (skips ~half the lines, 'worth about an order of magnitude', line 63-72).
- `parseClaudeLine`: requires `record.type==="assistant"`, reads `message.usage.{input_tokens,cache_read_input_tokens,cache_creation_input_tokens,output_tokens}`, `reasoningTokens:0` (Anthropic folds thinking into output), timestamp from `record.timestamp`, cost from `record.costUSD` if present. Dedup key = `${messageId}:${requestId}` (matches ccusage's approach) because T3 Code writes one record per assistant content block and all repeat the parent's full `usage` object — 'Summing them overcounts by roughly 2.4x' (comment, lines 78-85).
- `parseCodexLine` with rolling `CodexScanState`: model carried forward from the most recent `turn_context` event (token_count events carry no model); dedups consecutive identical `last_token_usage` JSON signatures; input tokens computed as `max(0, input_tokens - cached_input_tokens - cache_write_input_tokens)` because Codex reports input inclusive of cache; reasoningTokens clamped to `min(outputTokens, reasoning_output_tokens)`. Fork/subagent handling: a forked rollout's `session_meta` carries `forked_from_id` or a `source.subagent.thread_spawn.parent_thread_id`; the parser suppresses the copied-parent-history burst using a `FORK_COPY_MAX_GAP_MS = 1000` heuristic — 'copies are written in one synchronous burst (observed gaps 0-40ms), while the child's first genuine usage event only lands after a real model turn (observed 5s+). ... ccusage uses the same threshold' (lines 171-178).

COST PROVENANCE (usagePricing.ts, contracts/usage.ts `UsageCostSource`): three explicit tags — `providerReported` (transcript carried an explicit cost, e.g. Claude's `costUSD`), `modelPriced` (matched against LiteLLM's `model_prices_and_context_window.json`, fetched from `https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json`, 24h TTL, cached to `<stateDir>/usage-model-rates.json`), `unpriced` (tokens known, no rate — counted in totals, excluded from cost; explicit denylist of `<synthetic>`, bare `opus`/`sonnet`/`haiku`/`fable` family names treated as ambiguous-across-generations and never priced). Cache reads/writes priced at Anthropic's discount/premium rates when LiteLLM provides them, else defaulted to plain input rate (never 'free'). Cross-file/session dedup and a persisted `(size,mtime)`-keyed scan cache live in usageScanCache.ts / usageAggregation.ts, with a `UsageSourceFingerprint = {hostId, provider, resolvedHomePath, volumeId(device:inode)}` (contracts/usage.ts:111-126) specifically so two servers reading the same physical directory (e.g. worktree servers) don't double-count, and two machines with the same hostname/path don't collapse into one source.

**Takeaway.** Usage/cost is scanned live from exactly two locations — `~/.claude/projects/**/*.jsonl` and `~/.codex/sessions/**/*.jsonl` (both home paths independently overridable) — with hand-tuned dedup heuristics (2.4x Claude overcounting, 1s fork-copy gap for Codex) and a three-way cost-provenance tag (providerReported/modelPriced/unpriced) backed by LiteLLM's public rate table; Cursor/Grok/OpenCode are entirely outside this system.

### 6. Session lifecycle derivation and documented race/tiebreak rules

apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts (2071 lines) is where every driver's canonical `ProviderRuntimeEvent` stream gets folded into orchestration `thread.session.set` commands; apps/server/src/orchestration/projector.ts's `settledTurnStateForSessionStatus` (lines 53-69) is 'the authoritative completion signal' per docs/internals/glossary.md's definition of 'Turn' — maps session status → `idle|ready`→`completed`, `error`→`error`, `interrupted|stopped`→`interrupted`, `starting|running`→`null` (turn stays unsettled).

Race/tiebreak rules are gated behind `STRICT_PROVIDER_LIFECYCLE_GUARD = process.env.T3CODE_STRICT_PROVIDER_LIFECYCLE_GUARD !== "0"` (line 100, on by default) and documented inline at lines 1499-1546:
- `conflictsWithActiveTurn = activeTurnId !== null && eventTurnId !== undefined && !sameId(activeTurnId, eventTurnId)` — an incoming event names a turn different from the one the projection thinks is active.
- `missingTurnForActiveTurn = activeTurnId !== null && eventTurnId === undefined` — an untargeted event arrives while a specific turn is active.
- Exception carve-out (documented, lines 1503-1508): 'A turn.started that conflicts with the active turn is legitimate when the server itself has a turn start pending for this thread AND the provider session already tracks the event's turn as its active turn: steering a running turn makes some providers (e.g. opencode) open a new turn without ever completing the superseded one. A stale turn.started for some other turn id still gets rejected.' — computed as `conflictingTurnStartIsPendingTurnStart`.
- `shouldApplyThreadLifecycle` switch (1519-1545): `session.exited`/`session.started`/`thread.started` always apply; `turn.started` applies only if `!conflictsWithActiveTurn || conflictingTurnStartIsPendingTurnStart`; `turn.completed` is rejected outright if `conflictsWithActiveTurn || missingTurnForActiveTurn`, else 'Only the active turn may close the lifecycle state' (`sameId(activeTurnId, eventTurnId)` when both are known); when no active turn is tracked, an untargeted completion is rejected — documented reason: 'the known emitter was the Claude resume handshake (system/init + result(num_turns: 0)), which is not a turn at all — and applying it here stomps the starting lifecycle state while a turn start is pending.'
- Status derivation per event type (1560-1580): `session.state.changed`→mapped via `orchestrationSessionStatusFromRuntimeState` (starting/running+waiting→running/ready/interrupted/stopped/error) with a special case: if a turn-start is pending and the mapped status is `ready`, it's forced back to `starting`; `turn.started`→`running`; `session.exited`→`stopped`; `turn.completed`→`error` if `normalizeRuntimeTurnState(state)==="failed"` else `ready`; `session.started`/`thread.started`→`running` if a turn is active, `starting` if pending, else `ready` (comment: 'Provider thread/session start notifications can arrive during an active or pending turn; preserve that lifecycle state').
- `normalizeRuntimeTurnState` (257-269) canonicalizes any driver's raw turn-end reason to `completed|failed|interrupted|cancelled`, defaulting unknown values to `completed`. Every ACP adapter feeds this from its own `stopReason` field — e.g. CursorAdapter.ts:1041 and GrokAdapter.ts:1189 both do `state: result.stopReason === "cancelled" ? "cancelled" : "completed"`, i.e. ACP's own stop-reason vocabulary is deliberately collapsed to a binary cancelled/completed at the adapter boundary before reaching the shared tiebreak logic.
- A parallel, separately-gated tiebreak exists for `runtime.error` (line 1868-1870): under the strict guard, a runtime error only mutates session state if `activeTurnId===null || eventTurnId===undefined || sameId(activeTurnId, eventTurnId)` — same 'only the event that names the active turn (or an untargeted thread-level error) may win' pattern.
Events also carry an optional `sessionSequence` number (surfaced into activity records at line 364-369 of the same file) used for ordering in the projected activity feed, though the primary tiebreak mechanism documented above is turn-id identity, not sequence numbers.

**Takeaway.** Lifecycle derivation is a single explicit state machine (`ProviderRuntimeIngestion.ts`) that every driver's canonical event stream must satisfy; the documented tiebreak rule is 'only the event naming the currently-active turn id may close/mutate lifecycle state', with one named, commented exception for OpenCode's steer-a-running-turn behavior and one named exception for Claude's non-turn resume handshake — both race conditions were clearly hit in production and hard-coded as guarded carve-outs, not inferred.

### 7. Testing approach for drivers

No single shared 'driver contract test harness' exists for providers (unlike VCS, which has `apps/server/src/vcs/testing/VcsDriverContractHarness.ts`) — testing is per-driver and matched to how that driver actually talks to its CLI/SDK:
- **Claude** (in-process SDK): ClaudeAdapter.test.ts substitutes a hand-written `FakeClaudeQuery implements AsyncIterable<SDKMessage>` for the real `@anthropic-ai/claude-agent-sdk` query object — no subprocess involved at all, so tests inject synthetic SDK messages directly.
- **Codex** (own JSONL/app-server protocol): two techniques — (a) `codexCollabMockPeer.mjs`/`.sh` (apps/server/src/provider/testFixtures/) is a real mock child process spawned for multi-agent collab tests; (b) fixture-replay regression tests pinned against a REAL capture: `codexMultiAgentWire.json`, with the header comment stating exactly why (CodexCollabWire.test.ts:1-13): 'The child-interception path is the highest-blast-radius code in the subagent stack ... Three shipped bugs came from that decision being implicit ... These tests pin the decision against a REAL capture rather than hand-written shapes. Fixture provenance: codex-cli 0.145.0 driven directly over stdio with gpt-5.6-luna at low effort, prompting a two-child fan-out (alpha, beta).'
- **Cursor/Grok (ACP)**: tests spawn a REAL subprocess mock agent implementing the actual ACP protocol using the same `effect-acp` `AcpAgent` server API the shipped Grok/Cursor CLIs would use (packages/effect-acp/test/fixtures/acp-mock-peer.ts, and scripts/acp-mock-agent.ts referenced from GrokAdapter.test.ts) — i.e. the library dogfoods itself as both client and server in tests. The mock agent supports env-var-driven fault injection: `ACP_MOCK_MALFORMED_OUTPUT=1` writes literal `{not-json}` to stdout, `ACP_MOCK_EXIT_IMMEDIATELY_CODE=<n>` exits immediately with that code, used to test malformed-output and early-exit handling. GrokAdapter.test.ts additionally builds a temp-dir shell wrapper script (`fake-grok.sh`) that `export`s extra env vars before exec'ing the mock agent, so the driver's real `binaryPath`-resolution and env-merging code path is exercised end to end, not bypassed.
- **OpenCode**: `opencodeRuntime.cliParsers.test.ts` exists (parser-level unit tests), consistent with OpenCode being the one driver that talks HTTP to a spawned `opencode serve`-style process via `@opencode-ai/sdk/v2`.
All driver test files use `@effect/vitest`'s `it`/`assert`/`TestClock` (Effect's deterministic virtual-time test clock) to control timeouts (e.g. the ACP session-load-timeout/replay-idle-gap) without real sleeps.

**Takeaway.** No generic driver-contract test suite; each harness is tested against something that speaks its real wire format — a fake in-process SDK object (Claude), a captured-from-production wire-trace fixture plus a real mock subprocess (Codex), or a real ACP-protocol mock agent process built from the same effect-acp library the production adapters use (Cursor/Grok) — with fault-injection via env vars for process-exit and malformed-output edge cases.

Directly relevant to JR-BAR's own multi-fork, multi-provider posture.
2. **`UsageCostSource` three-way provenance tag (`providerReported`/`modelPriced`/`unpriced`)** plus the LiteLLM public rate table as a free, auto-updating cross-vendor pricing source (24h-cached, offline-fallback) — directly answers the owner's open question about Claude's weekly-cap/Fable sub-cap policy indirectly: t3code does NOT attempt to model subscription caps at all, it only computes API-equivalent cost from raw tokens and is explicit that 'costUsd is the raw API-equivalent cost of these tokens. It is not money spent: subscription plans bill separately' (usage.ts:77-79) — i.e., they deliberately did not solve the cap-tracking problem JR-BAR needs to solve; this is a gap, not a pattern to copy, and the owner's Fable/weekly-cap question remains UNVERIFIED by this investigation (no code in t3code models subscription usage caps/blocking thresholds at all).
3. **`ProviderInstanceEnvironment` — a typed, redactable per-instance env-var overlay** (`{name, value, sensitive, valueRedacted}`, providerInstance.ts:104-113) merged via `mergeProviderInstanceEnvironment`, giving each account/instance isolated credentials/env without touching the parent process env — reusable for JR-BAR's multi-account-per-provider design.
4. **Two-tier telemetry gate (`STRICT_PROVIDER_LIFECYCLE_GUARD` env flag defaulting on)** wrapping newly-added race-condition fixes — lets a fix ship gated and be instantly disabled in the field without a redeploy if it regresses some driver's behavior; cheap insurance pattern worth copying for any new lifecycle-guard logic.
5. **Fork-copy suppression heuristic for Codex (1s gap) and the 2.4x Claude content-block overcounting fix** are narrow but exact bugs any from-scratch usage-scanner reimplementation will hit; copying the parsing logic verbatim (not just the concept) in usageTranscripts.ts avoids re-discovering both the hard way.
6. **Dogfooding pattern**: `effect-acp`'s `AcpAgent` server-side API is used to build both real Cursor/Grok drivers AND the test mock agents — worth copying as a testing philosophy if JR-BAR ever builds a generic-protocol adapter of its own.

**Takeaway.** Best transferable ideas: open/degrading driver-kind slugs, the three-way cost-provenance tag + free LiteLLM pricing table, and the per-instance redactable env overlay. Important gap, not a copy target: t3code explicitly does NOT model subscription weekly-caps or Fable-style sub-caps anywhere — it only prices raw API-equivalent token cost and says outright that isn't money spent — so the owner's Claude weekly-cap/50%-Fable-subcap claim is NOT confirmed or denied by this codebase and needs a separate, direct source (Anthropic's own docs/policy pages).

### Anthropic Claude (Pro/Max/Team/Enterprise) — window structure, confirmed live

### Cross-provider: what can be honestly computed vs must be estimated, and robustness guidance

HONEST/DIRECT-FROM-API (server is authoritative, no client math needed): Claude `five_hour`/`seven_day`/`seven_day_opus`/`limits[]` percentages; Codex `primary_window`/`secondary_window` used_percent + reset_at epoch; Cursor `usage-summary` included/on-demand + billing-cycle window; Gemini/Antigravity `remainingFraction`+`resetTime` per bucket; Devin daily/weekly percentages; Grok CLI/web billing percentage (when the endpoint works); Copilot `quotaSnapshots.*` percent-remaining (but NOT reset time).
